# v0.7.0 phase 1 — Exploratory orchestration benchmark

## Purpose

This benchmark compares three orchestration strategies over the same
deterministic procurement tools and business inputs:

1. Deterministic workflow: application-controlled tool selection.
2. Planner Agent: one LLM plan, validated sequential execution, final synthesis.
3. ReAct Agent: one observable decision after each tool observation.

It evaluates orchestration rather than arithmetic. All business calculations
come from the same Python tools.

## Environment

- Provider: LM Studio
- Model: `qwen/qwen3-8b`
- Thinking: disabled
- Maximum generation tokens: 384
- Maximum output tokens: 512
- Timeout: 240 seconds

Each value below is one selected manual execution. These results are
exploratory samples, not statistically reliable performance measurements.
Local model load, queueing, prompt processing, and streaming variability can
materially affect elapsed time.

Each mode executed eight business tools across the selected five cases (24
executions across all three modes).
Tool execution remained in the microsecond range; LLM requests dominated wall
time.

## Business assertions

The validated deterministic outputs were:

- Demand 120 GWh, supply 95 GWh: `SHORT`, position `-25 GWh`, volume to cover
  `25 GWh`.
- With spot 42 EUR/MWh: exposure `1,050,000 EUR`.
- Without spot: no economic exposure was calculated or invented.
- Demand 90 GWh, supply 100 GWh: `LONG 10 GWh`; spot coverage was unnecessary.
- Demand 100 GWh, supply 100 GWh: `BALANCED 0 GWh`; spot coverage was
  unnecessary.
- Explicit demand scenario +10% over 120 GWh: scenario demand `132 GWh`.

Scenario exposure was deliberately not inferred. It requires a corresponding
deterministic exposure tool execution with scenario demand; a model-generated
amount is rejected.

## Observed orchestration behavior

- Deterministic mode selected only the required tools in the tested cases.
- Planner and ReAct sometimes proposed spot exposure after a LONG or BALANCED
  result. The deterministic execution policy recorded the action as skipped and
  did not call the tool.
- The local model sometimes produced malformed or wrapped plan JSON. Balanced
  JSON extraction recovers presentation wrappers, while Pydantic and registry
  validation continue to reject invalid content.
- The model sometimes presented a SHORT deficit with a negative sign or added
  unsupported economic claims. Final-response validation replaced only the
  presentation with a canonical response based on executed tool results.
- ReAct initially attempted to finish the scenario case without executing the
  requested scenario. Evidence completeness now blocks premature completion and
  allows one bounded recovery decision.

## Interpretation

For this known procurement workflow, deterministic orchestration was faster,
simpler, and more precise in tool selection. Planner and ReAct demonstrate the
additional autonomy being studied, but they require explicit validation,
budgets, execution policies, and output grounding.

This phase does not establish that one mode is universally superior. It shows
the cost and safeguards associated with delegating a known workflow to an LLM.

## Follow-up benchmark requirements

A later benchmark should run each case repeatedly, preserve
`ExecutionComparisonRecord`, report median and percentile wall times, and count
plan failures, skipped actions, fallbacks, and successful completions. It must
not automatically execute all modes from a user-facing query until resource and
latency implications are made explicit.
